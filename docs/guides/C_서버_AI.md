## 지금 상태 요약
- ASP.NET Core(.NET 10) + SQLite, Azure App Service 배포 (`server/deploy-azure.sh`).
- API: 건물 목록·조회, 쪽지 목록·작성(사진)·조회·삭제. 테스트는 `server/KucaMemoServer.Tests`.

## AI 기능 공통 원칙
- 앱은 AI 를 직접 부르지 않고 **항상 이 서버를 거칩니다** (키 보호, 비용 통제, 모델 교체 쉬움).
- 키는 Azure 앱 설정 / 로컬은 `dotnet user-secrets`. 저장소에 넣지 않습니다.
- **AI 가 실패하거나 느릴 때의 대체 동작**을 반드시 둡니다 (규칙 기반 결과, 시간 초과).
- AI 응답은 자유 문장이 아니라 **정해진 JSON 형식**으로 받게 하고, 서버에서 형식을 검사합니다.
- 기획서 "품질 관리": 공지는 **원문 링크를 반드시** 함께 돌려줍니다.

**🟨 공통으로 결정할 것**
- 사용할 AI 서비스와 모델 (Gemini / Claude / 기타 — 무료 한도, 한국어 품질, 응답 속도 비교)
  결정: 학교 FactChat(챗쿠·BAZE) 게이트웨이, OpenAI Chat Completions 형식. 내용 검사는 `claude-haiku-5-5`, 산책 추천은 B 가 정한 `gpt-5.4-mini`. 키는 `Recommend:ApiKey` 하나를 같이 씀 — ocyu007-cloud, 10/9. 이유: 학교 제공, 글·사진 호출을 직접 확인함
- 하루 호출 상한, 같은 질문 결과 재사용(캐시) 여부
  결정: 상한·캐시 없음. 대신 시간 초과(15초)·장애 시 규칙 기반으로 대체 — ocyu007-cloud, 10/9. 이유: 학교 게이트웨이 크레딧으로 관리

## C-2. 쪽지 AI 필터 (R2, 필수)

**목표:** 기획서 "쪽지 내용 → 부적절한 내용 필터링".
**완료 기준:** 쪽지·댓글 작성 시 서버가 AI 로 판별하고, 부적절하면 저장하지 않고 이유를 돌려준다. AI 장애 시에도 작성 자체가 막히지 않는다.

**🟨 작업자가 결정할 것**
- "부적절"의 기준 (욕설, 혐오, 개인정보 노출, 광고, 수업·시험 정보 유출 등 무엇을 포함할지)
  결정: 욕설·혐오·성적 내용(`abusive`), 개인정보(`personal_info`), 광고·홍보(`advertising`). 수업·시험 정보는 제외 — ocyu007-cloud, 10/9
- 사진도 검사할지 (비용·속도 증가)
  결정: 쪽지 사진도 검사 (사진 1장 약 4,800 토큰) — ocyu007-cloud, 10/9
- AI 장애 시 정책 (일단 저장 후 나중 검사 / 단어 목록만으로 검사 / 거절)
  결정: 금지어 목록과 전화번호·이메일 패턴으로 검사 (`KeywordModerator`), 작성은 막지 않음 — ocyu007-cloud, 10/9
- 애매한 경우 처리 (거절 / 숨김 후 검토 대기)
  결정: 숨김 후 검토 대기 (`status: pending`, 작성 기기에만 보임). 관리자 API(`X-Admin-Key`)로 공개/삭제 — ocyu007-cloud, 10/9

**🔗 맞춰야 할 것:** 거절 응답의 상태 코드와 사용자에게 보일 문구 → B

**확인 방법:** 정상·욕설·전화번호 포함·광고 문장 등 예시 묶음을 테스트로 만들어 기대 결과와 비교.

## C-3. AI 맞춤 탐방 추천 API (R2, 필수 — 대표 기능)

**목표:** 기획서 "공강 시간과 현재 위치에 맞춰 안 가 본 장소로 가는 짧은 루트", "취향, 날씨, 계절감을 분석해 오늘 걷기 좋은 숨은 명소와 산책 코스를 큐레이션."
**완료 기준:** 앱이 보낸 정보로 장소 3~4곳의 순서와 장소별 한 줄 이유를 돌려준다. 실제 걸을 수 있는 거리·시간 안이다. AI 실패 시 규칙 기반 추천을 돌려준다.

**지금 자료:** `server/KucaMemoServer/Data/buildings.json` (건물 632개, 좌표), 앱의 경희스팟 목록(`Memo/KyungHeeSpots.cs`), 캐릭터 랜드마크 구역(`CreatureLibrary.GoldZones`)

**🟨 작업자가 결정할 것**
- 입력에 무엇을 넣을지 (현재 위치, 남은 시간, 방문 기록, 잡은 캐릭터, 취향, 날씨·계절)
  결정:
- 거리·시간 계산을 AI 에게 맡길지, 서버가 후보를 거리로 걸러서 AI 는 고르기·설명만 할지 (후자 권장: 엉뚱한 거리 방지)
  결정:
- 추천 후보 장소 목록 (632개 건물 전체 / 경희스팟·랜드마크만 / 직접 고른 숨은 명소 목록)
  결정:
- 숨은 명소에 대한 설명 자료를 누가 어떻게 모을지 (AI 가 학교를 잘 모르므로 직접 쓴 짧은 소개가 품질을 좌우)
  결정:

  결정:

**🔗 맞춰야 할 것:** 입력·출력 JSON → B. 출현 조건(A-1)을 추천 이유에 쓸지("지금 가면 밤에만 나오는 날다람쥐를 만날 수 있어요") → A

## C-4. AI 공지 판별 (R2)

**목표:** 기획서 "학교 공지사항을 올라오는 즉시 AI 가 판별하여 각 장소에 맞는 공지사항을 입력", "공지 사항의 링크를 무조건 첨부."
**완료 기준:** 공지 원문(제목·본문·링크)을 넣으면 관련 장소 ID 와 짧은 요약이 붙어 저장되고, 앱이 장소별 공지를 받아 갈 수 있다.

**🟨 작업자가 결정할 것**
- 공지 수집 방법 (학교 사이트 자동 수집 / 운영자가 붙여 넣기) — 자동 수집은 사이트 이용 규칙 확인 필요
  결정: 운영자가 붙여 넣기 (관리자 API `POST /api/admin/notices`, 원문 링크 필수) — ocyu007-cloud, 10/13. 이유: 사이트 이용 규칙·구조 변경 걱정 없음
- 장소와 무관한 공지 처리 (버림 / 전체 공지로)
  결정: 버림 (저장하지 않고 `200 {saved: false}`). 장소 후보는 경희스팟 25곳만 — ocyu007-cloud, 10/13. 이유: B 의 명세("장소와 연결되지 않은 공지는 넣지 않음")와 같음, 지도에 표시되는 곳과 맞춤
- 지금 앱의 `Data/Notices.json` 을 서버 공지로 대체할지
  결정: 장소 공지는 서버 `GET /api/notices` 를 씀 (앱은 서버에 공지 API 가 없을 때만 예시 공지를 보여 주도록 B 가 이미 처리, #19). 앱 전체 안내(환영 글 등)인 `Notices.json` 은 B 판단에 맡김 — ocyu007-cloud, 10/13
